## Response

The strongest idea across these documents is that the kit should move responsibility out of prompt prose and into explicit, inspectable boundaries. The failures described in `what-went-wrong.md` are not primarily failures of wording. They are failures of enforcement: an agent can acknowledge a rule, skip it, and still produce something that appears acceptable. Adding more instructions increases the surface area for contradiction without changing that incentive.

The current build target is GitHub Copilot, so using terms such as `agent`, `prompt`, and `instructions`—and Copilot’s corresponding file conventions—is appropriate. The kit should still avoid unnecessary architectural assumptions that would make a future host impossible. A useful middle ground is to classify each artifact as common, Copilot-specific, or not yet classified. That classification provides portability information now, while a second host remains out of scope, and gives the project a practical starting point for splitting common and host-specific artifacts when that host is added. Releases can then assemble the common artifacts with one host-specific version, much as programs build for multiple operating systems or architectures. The durable vocabulary is an operation, an agent that performs or coordinates it, instructions that guide the work, a prompt that invokes those instructions, and a contract that defines the boundary. Names such as `specify`, `change`, `plan`, `implement`, and `sync` identify operations within the Copilot build.

Contracts therefore need to be more than documentation. They should define the smallest useful input and output shape, make invalid states visible, and give the next agent enough information to reject an incomplete handoff. JSON is a good canonical representation for this because it makes structure unambiguous and supports validation and rendering. Human-readable Markdown should remain a view of the contract or its evidence, not the source of truth.

The distinction between a contract and evidence is important. A contract describes what must be true at a boundary; evidence shows why we believe it is true. Evidence should be tied to observable facts—such as a test result, a file or symbol, a diff, or an explicit unresolved issue—rather than merely an agent’s assertion that it followed a process. Otherwise, “only outputs matter” risks replacing one form of compliance theater with another.

The proposed lightness is not just a matter of shorter prompts. It is a matter of reducing the amount of state each agent must hold in context and reducing the number of decisions that are left implicit. Small composable prompts with narrow contracts can help medium models, but composition also has a cost: every handoff can lose context, introduce translation errors, or add ceremony. A useful component should earn that cost by making a boundary independently verifiable or reusable. Agents should coordinate prompts, while contracts should carry the durable state between them.

The initial agents and prompts should be usable enough to carry an exploratory project through the workflow and exercise those boundaries, but they are bootstrap implementations rather than a finished turnkey system. Once a main project begins, users should expect to make limited adjustments as its context and constraints reveal gaps. After the project’s approach is established, larger changes—or a complete replacement of an agent—become reasonable, provided the replacement adheres to the same contract. The contract is the durable target: implementations may change as long as they continue to accept and produce the agreed boundary data. This staged approach makes early use valuable because it exposes real contract gaps without requiring the kit to predict every project’s needs in advance.

That replaceability should come with a deliberate increase in agent autonomy. Agents should make frequent, short commits as they work, preserving a useful audit trail and making recovery straightforward. Humans should review the overall pull request and integrate it by merging to `main`; this is the intended source-control boundary, summarized as “agents commit, humans integrate.” Agents may create branches and follow-up commits within that boundary, but should not amend or rewrite published history, bypass required checks, broaden the authorized path or change scope, or perform destructive or externally visible actions without an explicit gate. CI validation, protected branches, clean handoff metadata, and an inexpensive revert path should enforce these boundaries. These safeguards matter because the workflow must remain trustworthy even when an agent ignores or misinterprets a rule; compliance should be observable at the PR and integration boundary rather than inferred from the agent’s claims.

The “pairs” idea is compelling where one agent’s success criterion is naturally different from another’s—for example, producing a failing test and then demonstrating that the implementation makes it pass. It should not become a universal requirement that doubles every step. The practical test is whether the separation creates an independent opportunity to detect a shortcut. If both sides can be satisfied by repeating the same unverified claim, the pair adds little.

The same principle applies to Inspect and Adapt. Lightweight issue capture during the main flow is valuable; an unconstrained prompt-review loop is exactly the spiral the history warns about. Prompts should record concrete inconsistencies as they are encountered, then return to the main flow. A final prompt can aggregate those observations after the change is complete and recommend adaptations. Adaptation should be bounded, distinguish a real defect from a possible concern or stylistic preference, and allow the human to resolve issues that do not justify more automation. The kit should make uncertainty explicit instead of forcing every observation into a rule.

The specification should define a feature, not a single change. It is a living source of truth that the `specify` prompt can create or update as the feature develops. A change should be anchored to that feature spec, but it also needs a separate, durable traceability artifact—such as a per-change plan or delta spec—that records the intended change, its relationship to the living spec, and the evidence produced while implementing it. This keeps the feature coherent without pretending that the whole feature is frozen for every change.

The living spec and the change artifact serve different purposes. The living spec describes the feature’s current desired behavior; the change artifact describes one bounded transition and provides the audit trail for it. A frozen snapshot can be useful as the implementation boundary for that transition, but it should be understood as a versioned view or delta—not as the permanent feature spec. During implementation, scope should remain anchored to the selected change. If the change can be completed as planned, finish it and then update the living spec as appropriate. If implementation reveals work that is not part of the planned change, do not force it into the current artifact: record it as follow-up work and give it its own change artifact. If the planned change cannot be completed, discard or restart that change’s work rather than corrupting the feature spec or silently broadening its scope. Keeping changes small makes that restart affordable.

The memory bank should follow the same boundary. The kit can provide a small starter set of project-context artifacts, but it should not require every project to use the same memory-bank structure. A project may replace or extend those artifacts as its needs become clear. The memory bank is durable context for agents, not a second specification system; its fields should earn their place by preventing repeated context loss or making an important decision inspectable. It should also record the authorization and evidence relevant to autonomous actions, so a later agent can verify what changed, under which scope, and which gates were satisfied.

Several principles reinforce one another:

- Well-formedness is the bootstrap layer. Before optimizing development behavior, every operation needs a valid input, a valid output, and a clear failure path.
- Verifiability is the trust layer. Entry and exit gates should be checkable from artifacts or execution results, not from obedience to prose. This is especially important as agents gain autonomy: permissions, scope, repository state, validation results, and exceptional decisions should be observable and independently checkable.
- Composability is the reuse layer. Shared contracts should allow interchangeable implementations without requiring agents to know each other’s prompts.
- Measurement is the learning layer. Prompt size, handoff count, failure rate, and review churn are useful observations, but none should become a success target by itself.
- Follow-up discipline is the scope layer. The workflow should keep each change bounded, preserve the living feature spec, and give genuinely new work a separate traceability artifact.

There is also a useful scope boundary in the problem statement. This kit is for recurring, medium-sized changes where the cost of heavyweight planning exceeds its value. It should be deliberately opinionated about its supported workflow and deliberately honest when a task falls outside it. “At least as good as existing spec-kit for the work I actually do” is a better bar than feature parity, and it gives the project permission to leave unsuitable use cases alone.

My current view is that the kit’s defining feature should be a small set of machine-checkable contracts and evidence-bearing transitions, with prompts treated as replaceable implementations. If a behavior matters, the system should make violating it observable at a boundary. If it cannot do that, the behavior is guidance or preference—not a guarantee—and should be described accordingly.
